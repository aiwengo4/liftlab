# Разбор расчётной модели сайта liftsim

> [!warning] Внешний референс
> Это анализ стороннего сайта по состоянию на указанную дату, а не спецификация LiftLab. Актуальные правила нашего проекта находятся в `SPECIFICATION.md`, параметры — в `INPUT_PARAMETERS.md`.

Эта заметка фиксирует фактические формулы и правила публичного сайта
«Симулятор офисных лифтов» по состоянию на 3 сентября 2026 года. Она нужна как
справочник для точечных запросов без повторного анализа JavaScript сайта.

## Краткий вывод

Из сайта стоит перенять структуру `Passenger` / `Elevator` / `Queue` / `Event`,
очереди вверх и вниз, seeded RNG, сценарии рабочего дня, простую
диспетчеризацию как baseline и разделение ожидания и полного времени поездки.

Не стоит переносить без изменений линейную механику движения, фиксированное
время посадки, распределения спроса, шаг расчёта до 10 секунд и аналитику только
по доставленным пассажирам. Это хороший продуктовый прототип, но не точный
traffic simulator.

## Параметры по умолчанию

| Параметр | Значение |
|---|---:|
| Этажей | 7 |
| Лифтов | 2 |
| Вместимость | 14 человек |
| Разгон/торможение | 0,5 с |
| Движение на этаж | 4 с |
| Открытие дверей | 1,5 с |
| Закрытие дверей | 1,5 с |
| Посадка/высадка (`dwell`) | 4 с |
| Приход 80% сотрудников | 09:00–11:30 |
| Уход 80% сотрудников | 18:30–20:30 |
| Обед | 13:00–16:00 |
| Встречи | 11:00–19:00 |
| Смещение к целым часам | 50% |
| Заполнение переговорных | 40% |
| Доля идущих на обед | 60% |
| Минимальный интервал активностей | 60 минут |

Для каждого этажа задаются количество работников, места в переговорных и
признак остановки лифта.

## Движение и остановка

Движение линейное, без отдельной физики разгона и торможения:

```text
movement_time(A, B) = accelBrake + |B − A| × secPerFloor
```

Параметр `accelBrake` фактически является одной задержкой перед движением.

Остановка:

```text
stop_time = doorOpen + dwell + doorClose
```

Полный цикл от отправления с этажа A до закрытия дверей на B:

```text
service_leg_time =
  accelBrake
  + |B − A| × secPerFloor
  + doorOpen
  + dwell
  + doorClose
```

Пример 1 → 7 с настройками по умолчанию:

```text
movement_time = 0,5 + 6 × 4 = 24,5 с
service_leg_time = 24,5 + 1,5 + 4 + 1,5 = 31,5 с
```

В модели нет номинальной скорости, высоты этажей, ускорения в м/с², jerk,
выравнивания кабины и зависимости движения от загрузки. Для нашей первой
версии лучше использовать эмпирическую функцию `travelTime[floorDistance]`, а
не считать короткие и длинные поездки одной линейной формулой.

## Ожидание и полное время

```text
waiting_time = boarded_at − appeared_at_hall
total_time = delivered_at − appeared_at_hall
```

`boarded_at` присваивается всем вошедшим одновременно после завершения открытия
дверей. `delivered_at` присваивается после открытия дверей на целевом этаже.
Индивидуальный проход через двери и выход из кабины не моделируются.

Для нашей модели нужны отдельные моменты:

```text
hall_arrival
boarding_started
boarding_completed
car_departed
destination_arrival
exit_completed
```

Тогда:

```text
waiting_time = boarding_started − hall_arrival
in_car_time = exit_completed − boarding_completed
time_to_destination = exit_completed − hall_arrival
```

## Генерация прихода

Для каждого сотрудника создаётся одно утреннее событие.

```text
80%: Uniform(arrivalWindowStart, arrivalWindowEnd)
10%: до основного окна
10%: после основного окна
```

При стандартных настройках:

```text
80%: 09:00–11:30
≈10%: 08:00–09:00
≈10%: 11:30–18:30
```

Поздний интервал тянется до начала периода ухода, поэтому хвост получается
неестественно длинным.

### Смещение к целым часам

Для событий вне основного 80%-окна с вероятностью `hourBias / 100` выбирается
случайный целый час:

```text
time = whole_hour + Uniform(−10 минут, +5 минут)
```

Проводится до восьми попыток попасть в допустимый диапазон; затем используется
обычное равномерное распределение. `hourBias` не применяется к основным 80%
приходов и уходов, несмотря на возможное впечатление от названия настройки.

Рекомендуемая замена:

```text
arrival_time ~
  p_uniform × Uniform(window)
  + p_peak × PeakDistribution(anchor)
  + p_outlier × OutsideWindowDistribution
```

## Генерация ухода

```text
80%: Uniform(18:30, 20:30)
20%: biasedTimeBetween(20:30, 22:30)
```

Ранний уход не моделируется. Приход и уход генерируются почти независимо, без
модели продолжительности рабочего дня. Лучше генерировать длительность
присутствия условно на времени прихода и предусмотреть ранний, основной и
поздний уход.

## Обед

Участие:

```text
goes_to_lunch ~ Bernoulli(lunchShare / 100)
lunch_time ~ Uniform(lunchWindowStart, lunchWindowEnd)
actual_start = max(lunch_time, person.availableAt)
return_time = actual_start + activityDuration
```

Создаются поездки `рабочий этаж → лобби → домашний рабочий этаж`. При
стандартных настройках 60% людей ходят на обед ровно на 60 минут. Стоит
сохранить парные события и контроль пересечения активностей, но заменить
фиксированную продолжительность и равномерное начало эмпирическими
распределениями.

## Встречи

Количество участников для каждого этажа и слота:

```text
attendees = round(meetingSeats × meetingFill / 100)
```

Время отправления участника:

```text
meeting_trip_time = whole_hour + Uniform(−7 минут, +8 минут)
return_time = meeting_trip_time + activityDuration
```

Человек случайно выбирается среди свободных, находящихся не на этаже встречи и
успевающих вернуться до ухода. Сущности «встреча» нет: пассажиры генерируются
независимо. В нашей модели сначала следует создать встречу с общими `start`,
`duration`, `destination`, `attendee_count`, а затем назначать участников.

## Вместимость и посадка

Очереди обслуживаются FIFO:

```text
while queue_not_empty and passengers_in_car < capacity:
    board(first_passenger)
```

Вместимость считается только в людях. Вес и комфортная вместимость отсутствуют.
Все пассажиры входят мгновенно, а `dwell` не зависит от числа входящих и
выходящих.

Рекомендуемая формула:

```text
transfer_time = max(
  minimum_dwell,
  exit_count × exit_time_per_person
  + enter_count × enter_time_per_person
  + congestion_penalty
)
```

## Диспетчеризация

Это простая collective-like эвристика, не оптимизатор и не destination control.

Если в кабине есть пассажиры:

1. Выбирается ближайший destination впереди по текущему направлению.
2. Если впереди назначений нет — ближайший destination независимо от направления.
3. Ради внешнего вызова лифт обычно не отклоняется, но подбирает людей на этаже,
   где всё равно остановился для высадки.

Если лифт пуст:

1. Ближайший совместимый вызов по направлению.
2. Граничный вызов противоположного направления.
3. Ближайший вызов вообще по `|callFloor − position|`.

Возраст вызова, размер очереди, ETA, загрузка соседних кабин и будущие остановки
в стоимости не участвуют. Второй лифт не отправляется на этаж, который уже
обслуживается первым; при большой очереди это может мешать подать две кабины.

Эту эвристику стоит оставить как `baseline_dispatcher`. Следующий алгоритм
может минимизировать:

```text
cost(elevator, call) =
  a × ETA
  + b × extraStops
  + c × occupancy
  + d × callAge
  − e × queueSize
```

## Парковка

- Утренняя парковка: свободные кабины направляются на первый этаж во время окна
  прихода.
- Вечерняя парковка: после 20:00 свободные кабины направляются к ближайшему
  обслуживаемому этажу около `ceil(floorCount / 2)`.
- Открытые двери в лобби: утром свободная кабина на первом этаже держит двери
  открытыми, пассажир садится без времени открытия.

Это полезные переключаемые стратегии для сравнительных сценариев.

## Лестница и этажи без остановки

```text
walkOneFloor and |destination − origin| = 1 → пешком
```

Для необслуживаемого этажа выбирается сначала ближайший обслуживаемый этаж выше,
а при его отсутствии — ниже. Есть отдельное асимметричное правило для одного
этажа вверх без остановки. Лучше заменить это вероятностной моделью
`P(walk | distance, direction, queue, accessibility)`.

## Случайность и воспроизводимость

Используется линейный конгруэнтный генератор:

```text
seed[n+1] = (1664525 × seed[n] + 1013904223) mod 2^32
U[n] = seed[n] / 2^32
```

Seed одиночного прогона — `20260530`. Для пакетных прогонов:

```text
seed[i] = (20260530 + i × 1013904223) mod 2^32
```

Seeded RNG нужно перенять, но на сайте seed не показывается и не сохраняется в
URL как самостоятельная часть прогона. В нашей модели пользователь должен
видеть, повторять и менять seed.

## Метрики сайта

```text
average_wait = Σ(boarded − arrival) / delivered_count
average_total = Σ(delivered − arrival) / delivered_count
```

Медиана считается стандартно по отсортированному массиву. Также выводятся число
доставленных, пришедших на работу, ушедших домой, ожидающих сейчас и почасовые
медианы.

Гистограмма использует интервалы:

```text
0–30, 30–60, 60–90, 90–120, 120–180,
180–240, 240–360, 360–600, 600–900, 900–1200+ секунд
```

Час определяется по времени появления пассажира, а не доставки:

```text
hour = floor(arrival / 3600)
```

Для десяти прогонов сайт усредняет run-level медианы:

```text
batch_median_wait = mean(median_wait каждого прогона)
```

Это не pooled median всех пассажиров, поэтому показатель следует называть
«средняя медиана по прогонам».

## Критичные ограничения аналитики

Метрики считаются только по `delivered` пассажирам. Оставшиеся в очереди к
концу дня полностью исключаются из ожидания и полного времени. Это survivor
bias: при перегрузке самые проблемные пассажиры исчезают из статистики.

В модели отсутствуют:

- P90/P95/P99 ожидания;
- максимальная, средняя и интегральная очередь;
- возраст самого старого вызова;
- доля не попавших в первую кабину;
- количество пропущенных кабин;
- загрузка по участкам и доля полных отправлений;
- handling capacity за пять минут;
- service interval и round-trip time;
- число остановок и пустые пробеги;
- время кабин в состояниях `moving`, `door`, `idle`;
- корректный учёт незавершённых пассажиров.

## Ограничение симуляционного шага

Сайт исполняет симуляцию шагами до 10 виртуальных секунд. Внутри шага сначала
добавляются пассажирские события, затем лифты обновляются сразу на всю длину
шага. При смене состояния кабины остаток шага может потеряться. Поэтому времена
имеют погрешность и ядро не является полноценной дискретно-событийной моделью.

Наша модель должна переходить строго к ближайшему событию:

```text
next_time = min(
  nextPassengerArrival,
  doorOpenCompleted,
  boardingCompleted,
  doorCloseCompleted,
  elevatorArrived
)
```

Скорость анимации не должна участвовать в расчёте.

## Решение по переносу

| Компонент | Решение |
|---|---|
| `Passenger`, `Elevator`, `Queue`, `Event` | Перенять |
| Очереди отдельно вверх/вниз | Перенять |
| Seeded RNG | Перенять, seed показывать и сохранять |
| Этажи, население, переговорные | Перенять |
| Парные поездки на обед и встречи | Перенять концепцию |
| Разделение wait и total time | Перенять |
| Простая диспетчеризация | Оставить как baseline |
| Эмпирические сценарии парковки | Перенять |
| `этажи × секунд/этаж` | Только временно для MVP |
| Фиксированный dwell | Заменить зависимостью от потока |
| Распределения прихода и ухода | Перепроектировать |
| Почасовые когорты | Перенять с явным определением |
| Среднее и медиана | Дополнить перцентилями и SLA |
| Расчёт только по доставленным | Не переносить |
| Шаг до 10 секунд | Не переносить |
| Скрытый фиксированный seed | Не переносить |
