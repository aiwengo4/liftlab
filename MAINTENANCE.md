# Обновление и сопровождение LiftLab

## Постоянные адреса

- Сайт: <https://aiwengo4.github.io/liftlab/>
- Репозиторий: <https://github.com/aiwengo4/liftlab>
- История публикаций: <https://github.com/aiwengo4/liftlab/actions>

## Обычный выпуск изменений

Работа выполняется в локальной папке проекта. Перед отправкой:

```bash
npm test
npm run build -- --base=/liftlab/
```

После успешных проверок:

```bash
git status
git add <изменённые файлы>
git commit -m "Краткое описание изменения"
git push
```

Каждый `push` в ветку `main` автоматически запускает `.github/workflows/deploy-pages.yml`. Workflow повторно устанавливает точные зависимости, запускает тесты, собирает `dist` с базовым путём `/liftlab/` и публикует его только при успехе всех шагов.

## Проверка публикации

Статус последнего запуска:

```bash
gh run list --repo aiwengo4/liftlab --workflow deploy-pages.yml --limit 1
```

Подробный просмотр выполняющегося запуска:

```bash
gh run watch <run-id> --repo aiwengo4/liftlab --exit-status
```

После зелёного статуса нужно проверить публичный адрес, вкладку алгоритма, запуск короткого сценария и ссылку `#settings=`. GitHub может до 10 минут отдавать предыдущую версию из кеша.

## Если публикация не прошла

1. Открыть неудачный запуск в GitHub Actions.
2. Получить журнал: `gh run view <run-id> --repo aiwengo4/liftlab --log-failed`.
3. Исправить причину локально и повторно запустить тесты и сборку.
4. Создать новый коммит и выполнить `git push`.

Не нужно вручную загружать папку `dist` или редактировать опубликованные файлы: Pages всегда строится из исходников ветки `main`. Неудачный workflow не заменяет последнюю исправную версию сайта.

## Воспроизводимый сценарий проверки

Минимальный smoke-test:

1. 7 этажей, 60 сотрудников, распределение «Поровну».
2. 2 лифта, Global FIFO.
3. Запустить расчёт и дождаться результатов.
4. Переключить стратегию на «Сначала ближайший вызов» и повторить.
5. Создать ссылку с `#settings=` и открыть её в новой вкладке.
6. Сохранить сценарий и убедиться, что он появился в локальной библиотеке.

При seed `42` контрольный публичный прогон 15 сентября 2026 года дал 569 маршрутов; среднее ожидание 13 с, P90 ожидания 27 с, среднее полное время 18 с и максимальную очередь 5. Изменение формул может осознанно изменить числа — тогда одновременно обновляются тесты, спецификация и этот контрольный результат.

## Проверка тяжёлых сценариев

Перед существенными изменениями ядра дополнительно проверяются:

- 4 000 сотрудников / 4 лифта / вместимость 10;
- 5 000 / 6 / 10;
- 10 000 / 10 / 10.

Проверка выполняется на одинаковой форме и seed в Chrome и Яндекс Браузере. Актуальные ориентиры времени находятся в `PERFORMANCE.md`.

## Зафиксированные некритичные замечания

| Приоритет | Замечание | Влияние |
|---|---|---|
| низкий | Нет `favicon.ico`, запрос возвращает 404 | Только отсутствие собственной иконки вкладки |
| низкий | При части невалидных значений кнопка расчёта выглядит активной | Нажатие безопасно блокируется, ошибки показываются; Worker не запускается |
| технический | Старый `scripts/browser-acceptance.mjs` может ошибочно сообщить о сбросе численности после возврата со вкладки методики | Отдельные проверки Chrome и Яндекс Браузера подтвердили, что данные формы сохраняются; требуется улучшить селектор теста |

## Правила безопасности

- Не добавлять в репозиторий пароли, токены, cookies, `.env` и персональные данные.
- Не коммитить `node_modules`, `dist`, `*.tsbuildinfo` и посторонние рабочие папки — они исключены в `.gitignore`.
- Не переписывать опубликованную историю через force-push без отдельного осознанного решения.
- Сценарии из `localStorage` существуют только в конкретном браузере; для передачи использовать `#settings=`.

## Что обновлять вместе с кодом

- правила модели → `SPECIFICATION.md` и вкладка `MethodologyView.tsx`;
- поля и диапазоны → `INPUT_PARAMETERS.md` и тесты `scenarioForm`;
- интерфейс → `UI_DESIGN.md`;
- производительность → `PERFORMANCE.md` с датой и конфигурацией;
- архитектура или зависимости → `TECH_STACK.md`;
- публикация → `PUBLISHING.md` и этот документ.
